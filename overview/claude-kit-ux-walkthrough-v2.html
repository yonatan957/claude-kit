claude-kit — UX Walkthrough

SYNOPSIS
claude-kit init · config [<type>] [--recommended] · update · add|remove <type> <name> · list · check · --version
<type> = skills | agents | plugins | tools | mcps

This is the target experience — nothing here is implemented yet. Every transcript below is a mockup of how the tool should look and behave from the developer's terminal.

§2

The heart of it — claude-kit config

One interactive command, two steps: Picker → Configure. The picker lists every type the registry declares — skills, agents, plugins, tools, MCP servers — pre-checked with your current state. You move with the arrows, toggle with enter, and finish by scrolling to the bottom and approving. Every type is also reachable on its own with config <type>.

KeysThe whole interaction model

KeyMeaning — everywhere, no exceptions
↑ ↓move through the list
enterselect / unselect the highlighted row — and on the last row, approve & install
tabswitch between the main screen and search mode, either direction
ctrl-cquit without installing anything

One verb per key, no modes to remember: enter always means "act on the row I'm standing on". A one-line footer on every screen repeats it, so the UI never relies on the user remembering.

GateWhen does Recommended / Custom appear?

Decided by state, not history: the prompt shows iff installed.json contains no claude-kit-managed components. So a user who ran init, aborted, and comes back next week still gets it — and a user with an existing setup never sees it again; config opens straight into the picker, pre-checked.

yonatan@dev: ~ — claude-kit config (fresh machine)
$ claude-kit config          # installed.json is empty → ask once

? How would you like to set up?
 ❯ Recommended   select our suggested set, done in one step
   Custom        choose everything yourself

Recommended opens the picker with the blessed set already selected —
scroll to the bottom and approve, or change anything on the way down.
yonatan@dev: ~ — claude-kit config (existing setup)
$ claude-kit config          # managed components exist → no prompt
Opening picker — your current setup is pre-checked.

$ claude-kit config --recommended
Re-align with the blessed set: pre-selects it on top of your current state,
then opens the picker so you can see and change it before approving.

Under the hood

Five types, three handlers — the type list is data

The registry declares the types; the CLI only knows handlers. Five types today share three handlers, so most of what looks like five code paths is one:

TypeHandlerWhat install meansWhat remove means
skillscontentcopy skills/<name>/ → ~/.claude/skills/delete the copied files
agentscopy agents/<name>.md → ~/.claude/agents/
pluginsmarketplaceclaude plugin install <name>@base-kit --scope userclaude plugin uninstall
toolsscriptinstall.sh → inputs → config.sh → verify.shuninstall.sh, if declared
mcpssame, plus mcp_config injected into settings

A sixth type is a catalog edit, not a CLI release, as long as it maps to an existing handler. Picker, Configure, config, add/remove and list all read the type list from the registry. Only a genuinely new installation mechanism needs new code.

Two rules the CI gate must enforce now that plugins exist. A plugin can bundle its own MCP servers, so (1) a capability is delivered either as an mcps component or by a plugin, never both — otherwise a user ends up with two Jira servers in one session; and (2) no catalog plugin may declare an .mcp.json that fetches at launch, which would smuggle npx-at-startup past the guarantee we make for our own MCPs.

The CLI's loop is identical for every component: run install.sh if present → collect inputs (masked when sensitive) → run config.sh with inputs as env vars → inject mcp_config if present → run verify.sh. Removal is the mirror image: strip mcp_config from settings → run uninstall.sh if present → delete the secret file → drop the entry from installed.json. All per-program weirdness lives in the scripts, in the catalog, reviewed like any content.

uninstall.sh is optional. Without it, removal cleans up only what claude-kit owns — settings entry, secret file, state — and says so rather than pretending the binary is gone.

Guarantees the user can rely on

  • Settings are sacred: in claude_settings.json, only the mcpServers block is ever managed; everything else is preserved byte-for-byte.
  • Nothing runs until you approve: selecting and unselecting only changes the list. The single Approve & install row at the very bottom is the only thing that acts, and pending removals are flagged in red on their own rows above it.
  • Secrets are never stored by Base-Kit: inputs go to config.sh as env vars, land in their target (tool config or env.d/, chmod 600), and are forgotten. installed.json records only "<set>" and a timestamp.
  • Auth survives upgrades: update re-runs install scripts, never config — credentials stay put.
  • The CLI never upgrades itself: it only notifies; npm install -g claude-kit@latest is always the user's explicit action.
  • Your CLAUDE.md is never rewritten: the org baseline is a separate file (genie-claude.md); your own file gains one @-reference line and nothing else — ever.
  • Nothing external is required to have a working setup: skills and agents are files in our own catalog, plugins are vendored into it, MCP packages come from Artifactory. Every component installs from one git clone — an outside hub can be added as an extra source, never as a dependency.
  • Every component remembers where it came from: installed.json records each entry's source, so update refreshes it through the right channel — ours from the catalog, externally-sourced ones through their source, manually-added ones left alone.
  • Opt-in only: nothing new is ever installed without the user selecting it.
  • update never prompts: anything needing input becomes a pending item, reported at the end.
  • Idempotent: running any command twice in a row is always safe.

The architecture rule that keeps the future open

core/ never talks to a human. No print, no prompt, no exit. Core functions take inputs and return objects (or raise typed exceptions) — all rendering and asking lives in the frontends: commands/ (CLI), ui/tui.py (screens), and later web/ (local Flask UI). The picker, the approve row and the scoped filters are all frontend work — the counters and removal flags are just a render of core.plan(state, registry, selections) -> ChangePlan, which the future web UI will render as a page instead of a list.
core/plan.py + core/configure.py — the shape of every core module
def plan(state, registry, selections) -> ChangePlan:
    # pure read: diff of installs/removals + what will need configuring
    # drives the section counters and the red 'will be removed' flags

def apply(plan: ChangePlan) -> list[ApplyResult]:
    # what the Approve row calls — installs, removals, mcp_config injection

def pending(state, registry) -> list[ConfigStep]:
    # pure read: which components need configuring, with their input forms

def submit(step: ConfigStep, answers: dict) -> VerifyResult:
    # runs config.sh with answers as env vars, then verify.sh,
    # updates status — returns a result object; NEVER prints, NEVER prompts

# the TUI renders these with prompt_toolkit;
# the future web UI maps them to routes:
#   POST /api/plan        GET  /api/config/pending
#   POST /api/apply       POST /api/config/<name>/submit
§8

Telling the user there's an update

A SessionStart hook shows a one-line banner when Claude Code opens. The hook never checks anything — it reads a file written earlier by claude-kit check, so startup is never delayed.

PieceJobCost
claude-kit checkruns the network checks, writes state.jsonseconds — in the background
the hookreads state.json, prints a bannerinstant
claude-kit updatedoes the work, clears state.jsonwhen the user runs it

The hook shows what's already known, then spawns the next check detached — so the banner is at most one check old, and the session never waits:

plugins/claude-kit-notify/hooks/session-start.sh
#!/bin/bash
# 1. say what we already know — instant, no network
msg=$(jq -r '.message // empty' ~/.claude-kit/state.json 2>/dev/null)
[ -n "$msg" ] && jq -nc --arg m "$msg" '{systemMessage: $m}'

# 2. refresh for next time — detached, never blocks startup
( claude-kit check --quiet >/dev/null 2>&1 & )
exit 0

It ships as a plugin (claude-kit-notify), not as a settings edit — so claude-kit doesn't touch settings.json, and the user can turn it off with /plugin disable.
